# D-001 -- Record decisions with MADR 4.0.0 and the Doka profile

## Context and Problem Statement

Doka.Tabular makes many binding decisions about its public API, file formats,
persistence, and resource behavior. Readers of the repository need to find
each decision with its reasons and its evidence, and reviewers need a fixed
shape that makes missing parts visible. The repository must stand on its own:
a record may refer to other records and to public primary sources, but not to
material outside the repository.

## Decision Drivers

- Each relevant decision is findable, traceable, and reviewable in the
  repository.
- Records follow a published standard so readers know the structure.
- Status changes reflect actual acceptance by the accountable people, never a
  passing build.
- No tooling inside the repository has to be maintained for the records.

## Considered Options

- MADR 4.0.0 with the Doka profile, maintained by hand
- MADR 4.0.0 with a generator and a build gate
- Free-form decision notes in the documentation

## Decision Outcome

Chosen option: "MADR 4.0.0 with the Doka profile, maintained by hand", because
it gives a recognizable structure with explicit acceptance and evidence while
keeping the repository free of record tooling.

### Consequences

- Good, because every record has the same required sections, metadata, and
  history format.
- Neutral, because the folder keeps no index by hand; the records themselves
  are the list, so no second list can drift from them.
- Bad, because reviewers check the profile rules by reading; a malformed
  record is not caught by the build.

### Confirmation

- Performed 2026-11-17: every record in this folder was written from the
  template with the thirteen metadata keys and the required sections in order;
  an automated structural check of the generated files confirmed the presence
  of Good and Bad entries in each option and in the consequences.
- Performed 2026-11-21: all records were reviewed by the decision maker and
  accepted; each record carries the status change with its date.

## Pros and Cons of the Options

### MADR 4.0.0 with the Doka profile, maintained by hand

- Good, because MADR 4.0.0 is a published template whose sections readers
  recognize.
- Good, because the profile adds metadata, status transitions, and
  confirmation rules that make acceptance and evidence explicit.
- Bad, because conformance depends on review; nothing in the build rejects a
  malformed record.

### MADR 4.0.0 with a generator and a build gate

- Good, because a gate rejects malformed records automatically.
- Bad, because the repository would carry and maintain its own tooling, and a
  missing record entry could turn builds red for reasons unrelated to code.

### Free-form decision notes in the documentation

- Good, because notes are quick to write.
- Bad, because status, evidence, and replacements are not traceable, and
  decisions drift from the code unnoticed.

## More Information

The profile is described in [MADR-PROFILE.md](MADR-PROFILE.md) and the
starting point for a new record is [adr-template.md](adr-template.md). The
folder's [README](README.md) lists no records; status, dates, and relationships
are read only from the metadata of each record. A record may add flat keys and
sections beyond the profile's own when they do not change the meaning of a
profile or MADR element. Records are written in US English and ASCII.

### Re-evaluation Triggers

- The MADR project publishes a new major version.
- The profile is changed for other repositories that share it.
- Records are imported or generated by external tooling and the format must be
  aligned.
